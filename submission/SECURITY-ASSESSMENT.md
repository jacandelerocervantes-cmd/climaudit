# ClimAudit: security and data-integrity assessment

Date: 2026-10-17 (revised the same day after an independent claim-by-claim review of this document against the code). Scope: the backend in `backend/` (Python 3.12, FastAPI, SQLite) and its three ledger adapters (in-memory, direct Hedera testnet, Guardian 3.7.1). The web app in `web/` is covered in section 2b. This is a self-assessment of a hackathon prototype. It is not an external audit, not a penetration test and not a certification.

Method: design review against `RULES.md` (claims governance); one independent code review of the backend (29 findings, all fixed, with regression tests in `tests/test_review_fixes.py` and the review decisions D-130 to D-145 in the decision ledger); a second independent review of this document against the code (it corrected several statements, which are fixed below); 265 automated tests (2 live tests are skipped unless requested); and live runs on Hedera testnet and a local Guardian (see section 4).

## 1. What is protected and where the trust boundaries are

| Asset | Where it lives | Who may change it |
|---|---|---|
| Evidence and reports | SQLite database (system of record) | Roles through the API only |
| Audit trail | Hash chain in the database, mirrored as hashes on a Hedera topic | Append only; corrections are new events |
| Credit units | HTS token on Hedera testnet and balances in the database | Registry (issue), holders (transfer, retire) |
| Ledger and API keys | Environment variables of the backend process | Operator only |
| Third-party documents | Uploaded PDFs | Untrusted input, never executed |
| Public datasets | Open-Meteo, ESA WorldCover, Berkeley database | Third parties, treated as advisory |

Boundaries: (1) uploaded documents and any AI output are untrusted; (2) the ledger holds hashes, ids and token amounts only, no evidence and no personal data; (3) public data may inform a human but never changes a number or blocks a decision.

## 2. Threats, controls and residual risk

| # | Threat | Controls in place | Residual risk |
|---|---|---|---|
| 1 | **Hidden or injected instructions in a PDF** (indirect prompt injection) | A sanitizer removes hidden text before any model sees the document: text in white, text smaller than 2 pt, text more than 50 pt outside the page, text with opacity exactly 0, text covered by a later white rectangle, including inside form XObjects. Text that merely looks like an instruction (`INSTRUCTION_IN_DOCUMENT`) stays visible but is flagged; the flag blocks verification until a verifier overrides it with a reason. Hidden text found is reported (`HIDDEN_TEXT_IN_DOCUMENT`). | Not detected: text hidden behind images or clipping paths, partial transparency, non-white backgrounds, optional-content layers, unusual font mappings, annotation text. Text and CSV files only get invisible-character handling and phrase matching. The block rate was exercised on the 20 synthetic dossiers and unit cases only: **no detection-rate figure is claimed.** |
| 2 | **The AI invents or misreads a number** | The optional extraction agent is read-only: it has no tools and no ledger keys (it needs an Anthropic key). It is a library module and is not yet wired to an API route. The server-side gate runs on evidence posted with the `extractor` role: the quote must appear verbatim in the sanitized text, be at least 12 characters, contain the value as a whole token and contain a word that matches the kind label; the item then waits for a person to confirm it (owner, verifier or admin), and unconfirmed items block the VERIFIED transition and are ignored by the calculation. In the report, every number in the narrative must match a computed figure; otherwise the narrative is dropped and a non-overridable finding blocks verification. | The gate proves a value is in the text, not that the document is truthful, and the kind-label check is a keyword match. Evidence entered by an owner or admin is not checked against a document. The computed figures are still returned if the narrative is dropped; in this prototype the narrative is generated by code, not by a model. |
| 3 | **Wrong arithmetic or silent rounding** | The calculation uses Decimal only (floats appear only in advisory checks and the Benford screen). Inputs are typed with units. Every factor is a reference with a name, value, profile id, page and a verified flag; unverified parameters are listed in the report as a non-blocking `METHODOLOGY_PARAMETER_UNVERIFIED` finding. Uncertainty is the minimum and maximum over adverse and favorable corners. Issuance uses the lower bound and never exceeds the claim. Equations 3, 7 and 15 and TOOL12 Eq. 1 were checked against the PDF page images (decision ledger O-6). | The relative uncertainty applied to modeled inputs (0.10) is a documented assumption, not a measured value (O-5). Other equations were read from text extraction. |
| 4 | **Tampering with history** | Events are hash-chained over canonical JSON (RFC 8785 subset, integers only, NFC strings) with three literal test vectors. The hashes are published on a Hedera topic. An independent verifier re-walks the chain and compares it with the topic read back from the mirror node; a gap, reorder or foreign message is reported. | Hashes prove integrity **after ingestion**. Fraud before the evidence reaches the system is mitigated, not eliminated. If a database transaction rolls back after a hash was already published, the verifier reports a mismatch (an orphan message, open item O-14). |
| 5 | **Double counting** | Two layers: an exact key (the parcel key for soil application, the product batch id for non-soil) with the period, and a spatial check on H3 cells with periods derived server side from the application dates. A second batch on an overlapping parcel is refused (HTTP 409, `BATCH_PERIOD_OVERLAP`). A public-registry check (Berkeley database) adds an advisory finding if credits were already issued for the same project and vintage. | The key and the cell list are supplied by the client and the cells are validated for structure, not for geometry, so a registrant who invents a different parcel key and different cells defeats the guard. The guard covers this system only. The registry data is a snapshot published every few months, has no coordinates and no serial numbers, and Verra has no bulk data here (manual lookup link). |
| 6 | **Unauthorized actions** | Static bearer keys, compared in constant time; role permissions checked per action and per resource ownership; a closed state machine with an explicit list of allowed transitions; issuance only for the registry role (admin cannot issue); overrides are limited to verifier and admin, need a reason and are recorded in the audit trail as a hash of the reason. The extractor role can only propose evidence. | Prototype authentication: static keys held in clear in `CP_API_KEYS`, no expiry, no per-key rate limiting, no TLS termination in the app (run it behind a TLS proxy) and no CORS policy. `/health` needs no key and `GET /profiles` needs any valid key. The admin role is broad (it can submit, reject, confirm evidence and override findings) and there is no separation-of-duties check between verifier and registry identities. `/docs` and `/openapi.json` are served only when `CP_ENV=dev` (the default is `prod`). |
| 7 | **Double mint, replay and lost updates** | `Idempotency-Key` on every state-changing route (atomic claim, with a request hash; a stored response is replayed for 24 h and each state-changing request purges expired rows). Issuance uses a stable per-batch operation key, commits the mint intent before the ledger call and the recorded mint result right after it, so a retry reuses the recorded result and does not ask the ledger again. As a second layer the direct Hedera adapter looks up an earlier mint or burn through the transaction memo before sending a new one, and the Guardian anchor looks for an existing credential with the same event hash. Balances have a `CHECK (units >= 0)` and conditional debits; state is re-read inside each transaction. | A crash in the instant between the ledger accepting a mint and the result being recorded relies on the ledger-side memo lookup, which scans only the latest 100 transactions and lags by seconds on the public mirror node (open item O-19). One process only (a process-wide lock). |
| 8 | **Key and credential exposure** | Hedera, Guardian and Anthropic credentials come only from environment variables (the demo scripts may read a local `.env` that is git-ignored); secret settings are excluded from `repr`; the Hedera client is hard-wired to testnet and refuses any other `CP_HEDERA_NETWORK`; adapter error messages carry only exception names and status codes, and a test asserts the Guardian password never appears. There is no logging module, so nothing is logged. | The mirror-node and Guardian URLs are operator-configured and not restricted. The Hedera operator account is also the token treasury and holds the supply key; the Anthropic and Hedera keys live in the same process. Production would need separate keys and a hardware or managed signer. |
| 9 | **Leaking sensitive data** | Only event hashes, ids and token amounts go to the ledger. Parcel locations are H3 cells (low resolution). All demo data is synthetic and labelled `SYNTHETIC_DEMO_DATA`. While `CP_FORCE_SYNTHETIC` is on (the default), project creation refuses non-synthetic provenance. | The flag can be switched off by the operator. The database is not encrypted at rest. |
| 10 | **Unavailable or wrong third-party data** | Public-data checks are advisory, run before the verification transaction opens, and fail soft with an info finding. Ledger failures fail closed (`LEDGER_UNAVAILABLE`, `LEDGER_REJECTED`). The Guardian anchor is read back before it is reported; for the direct adapter the audit-verify route reads the topic back and compares it with the local chain. | A dataset can be wrong (one 2021 land-cover pixel, ERA5 reanalysis); a human reviews every finding. |
| 11 | **Resource exhaustion** | Request bodies above twice the upload limit are refused with 413 while they are read, chunked ones included; `content_base64` and the evidence `span` have schema limits; a batch holds at most 20 documents; PDF parsing is capped at 200 pages and 300,000 operations. | There is no decompressed-stream cap in the PDF parser (which runs in the request thread) and no global rate limit. Not hardened for hostile traffic. |
| 12 | **Supply chain** | Few dependencies; optional ones (Hedera SDK, h3, rasterio, openpyxl, Anthropic) are extras. | Dependencies are version-bounded but **not pinned with hashes**. |
| 13 | **Token model** | One base unit equals 1 kg CO2e and the token has 3 decimals, so one displayed token is one tonne. Mint on issue, burn on retire. | Transfers between holders are custodial bookkeeping in the database and the audit trail, not on-chain transfers; holders have no Hedera accounts in this prototype. A transfer goes only to the actor id of a known owner or holder key; a real deployment needs an identity registry. |

## 2b. Web app (`web/`)

| Risk | Control | Residual |
|---|---|---|
| API keys reach the browser | Demo keys live in server environment variables (`CP_KEY_<ROLE>`, never `NEXT_PUBLIC_`); a same-origin proxy adds the `Authorization` header; the browser only holds an http-only cookie naming the demo role | The role selector is a demo device, not authentication. A real deployment needs real sign-in. |
| The proxy becomes an open relay | Only an allowlist of API routes is forwarded, the request body is size-limited, the target URL comes from server configuration | A new backend route must be added to the allowlist on purpose |
| A public link changes data or spends testnet fees | Recorded-run mode (`CP_SNAPSHOT=1`) answers reads from a file and refuses every write with `SNAPSHOT_READ_ONLY`; it needs no API and no key | The file is a recording: it proves what happened in that run, not the state of any live system |
| Script injection through text from documents or the backend | React escapes all text; there is no `dangerouslySetInnerHTML`; document text is shown after the backend sanitizer | A malicious string can still be misleading as text |
| Clickjacking, content sniffing, referrer leaks | Response headers set in `next.config.mjs` (`X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, `Permissions-Policy`) | No Content-Security-Policy yet |
| Dependency vulnerabilities | `npm audit` reports 0 known vulnerabilities for the web app and the demo tooling on 2026-10-18; lockfiles are committed | Re-run before any deployment |
| Accessibility barriers | Automated axe audit on every page and batch tab in the test suite; contrast checked for both colour modes | Automated checks do not replace testing with assistive technology |

## 3. Data integrity chain, end to end

1. Evidence enters with a SHA-256 of each file and typed, unit-checked values with provenance (`measured`, `modeled` or `synthetic`).
2. Verification runs deterministic code and records the profile id, every parameter reference and the calculation steps in the report.
3. The report and every state change become audit events, hashed over canonical JSON and chained to the previous event.
4. Each event hash is published (HCS topic directly, or as a signed credential in a Guardian policy that is read back).
5. Anyone can read the topic from a public mirror node and compare it with the exported chain; the audit-verify route does this automatically.

## 5. Known limitations (stated, not hidden)

- Not claimed: that AI replaces verifiers, that blockchain makes bad source data good, that testnet tokens are real credits, any detector accuracy or block-rate number, any zero-knowledge or fine-tuned model result.
- No external security audit or penetration test has been done.
- Authentication is a prototype (static keys). A real deployment needs OIDC or mTLS, key rotation, rate limiting, request-size enforcement and an HSM or managed signer.
- Single process and SQLite; a multi-process deployment needs a database with row locks.
- The VM0044 defaults and tool factors come from the published PDFs read on 2026-10-16; the profile flags every value that was not independently verified.
- Public datasets are snapshots; WorldCover and weather thresholds are screening heuristics, not methodology rules.

## 6. Next steps if the project continued

Pin dependencies with hashes; add rate limiting, CORS and TLS configuration, PDF decompression limits; replace static keys and add separation of duties; make transfers on-chain with per-holder accounts; encrypt the database; commission an external review; build an injection test set large enough to report a measured detection rate; wire the extraction agent to an API route behind the same gate.
